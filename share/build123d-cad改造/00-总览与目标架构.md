## 1. 改造背景

现有 `build123d-cad` 是一个**纵向单 skill**：围绕 build123d 把 CAD 建模 + 装配 + URDF + PyBullet
仿真吃透到工程级方法论（5 个 Playbook、三层验证、Dave Cowden / Peter Corke 哲学）。
内功扎实，但有两类问题：

1. **出工链路缺失**：激光切割预检、切片预检、SRDF/SDF、headless 渲染都没有或不完整。
2. **组织方式不利于扩展与测试**：所有能力堆在一个 1535 行 SKILL.md 里，改一处无法局部回归，
   也无法按子能力单独测试。后续要加 PCB / 电子 / 固件域时无处安放。

对照 `earthtojake/text-to-cad`：它把每个能力做成一个独立 sibling skill（9 个），
能力铺得开但安装分散、无统一方法论。

## 2. 目标形态

**一个父 super skill 内含 N 个子技能（monorepo 模块化）**：

- 一次安装即得多技能；
- 每个子技能独立 `SKILL.md / references / scripts / tests / benchmarks`，可单独 `pytest`；
- earthtojake 的横向能力**全部内化复刻**，不依赖外部 sibling；
- 扩新域 = 新增一个 `skills/<name>/` 目录（见 08 的 adding-new-subskill 流程）。

## 3. 目标目录骨架

```
build123d-cad/                       # 父 super skill
├── SKILL.md                         # 父级路由 ≤ 200 行：需求 → 哪个子 skill
├── README.md                        # 子技能架构说明（给开发者）
├── skills/                          # 子技能集合，每个可独立测试
│   ├── mechanical/                  # 子1 机械建模（根基，迁移现有内容）→ 文档 02
│   ├── viewer/                      # 子2 网页多引擎预览容器 → 文档 03
│   ├── urdf/  srdf/  sdf/           # 子3-5 机器人描述 → 文档 04
│   ├── gcode/ sendcutsend/ bambu-labs/ parts-catalog/  # 子6-9 制造出工 → 文档 05
│   ├── pcb/  electronics-bom/       # 子10-11 电子域占位（P3）→ 文档 06
├── shared/                          # 跨子技能协议 → 文档 08
│   ├── handoff-protocols.md
│   ├── multi-skill-router.md
│   └── dependencies.md
├── tests/                           # 父级跨子技能集成测试 → 文档 07
└── docs/                            # architecture.md / adding-new-subskill.md
```

> 每个子技能内部仍按 earthtojake 标准：`SKILL.md + references/ + scripts/ + tests/`。

## 5. 五大架构原则(含正反例)

1. **两层路由**:父 SKILL 只列表 + 关键词触发;LLM 进入子 skill 后再读详细 references,父级不读完整子内容。
   - ✅ 父 SKILL 200 行,viewer 子 SKILL 250 行,相加 < 单一 monolith 的 1/3 token
   - ❌ 父 SKILL 把 mechanical 的 5 个 Playbook 全 Inline 进来 → token 爆 + 改一个 Playbook 全 reload
2. **子技能自治**:每个子技能必须有 `SKILL.md + README.md`,外加 `references/ scripts/ tests/` 至少一项。
   - ✅ `skills/parts-catalog/{SKILL.md, README.md, scripts/find_part.py, tests/test_find.py}` 即合规
   - ❌ 一个子技能只放 SKILL.md 没 tests/ → CI 红
3. **零互引用**:子技能之间**不直接引用**彼此的 references,跨技能调用一律走 `shared/` 协议(防耦合)。
   - ✅ urdf 读 `output/<task>/joints.yaml`(mechanical 写),走 `shared/python/handoff/validate.py`
   - ❌ urdf 内部 `from skills.mechanical.references.simulation import xxx` → 强耦合,被 CI grep 拦截(见 [08 §10 验收](08-shared跨子技能协议.md))
4. **文件标准接口**:子技能间不做函数调用,通过约定的输出文件路径交换(如 mechanical 出 `output/<task>/parts/<part>.step`)。
   - ✅ 路径 + 字段 schema 在 [08 §2.0/§2.1](08-shared跨子技能协议.md) 锁定
   - ❌ 在父级用 `import` 让 mechanical 进程把 `Part` 对象传给 urdf → 跨进程依赖,不可独立测
5. **可独立测试**:改 viewer 只跑 `pytest skills/viewer/tests/`;父级 `tests/` 只测跨子技能流程。
   - ✅ `cd skills/viewer && pytest tests/` 秒级反馈
   - ❌ viewer 单测必须先调 mechanical 跑出 STEP → 一处变全跑,违反「秒级反馈」

## 5.A 角色与认领边界(谁动谁不动)

为了避免 11 个子技能 + 8 篇文档的协作互踩,边界规则:

| 角色 | 可动 | 不可动 | 评审权 |
|---|---|---|---|
| tech_lead | `SKILL.md`(父) / `shared/**` / `docs/**` / `pyproject.toml` | 任何 `skills/<name>/` 内部实现 | shared 改动 + 新加子技能 PR |
| 子技能 Owner(如 mechanical) | `skills/<我的>/` 全部 + 在 [08 §8](08-shared跨子技能协议.md#8-变更登记sharedchangelogmd) 登记自己引发的跨技能变更 | 别人的 `skills/<name>/`、shared 协议 | 自己技能内的实现细节 |
| 协作人 | 在被协作的子技能里 PR + Review | 直接 push 到别人的子技能 | — |
| project_manager | 01 文档 / 跨任务排期 / Gate 推送 | 任何 `skills/<name>/` 与 `shared/` 实现 | 排期/Gate |
| testing | `tests/`(父级) / `skills/*/tests/` 模板初稿 / `benchmarks/run_all.py` | 子技能业务逻辑 | smoke / benchmarks 通过标准 |

> 跨边界改动通过 PR + 评审,不绕路。文档层(本目录 share/)所有 Owner 都可改自己负责的章节,改其他人章节走 `[[评审建议]]` 留批注。

## 6. 不做什么(防 scope 蔓延)

- ❌ 不做 git submodule(子技能是目录,不是独立仓库;monorepo 一次安装即得多技能)
- ❌ 不改 skill 名字(暂留 `build123d-cad`,多域成熟后再议改 `hardware-design`)
- ❌ 不碰 5 个 Playbook 内容(只搬位置 + 改 references 路径前缀,见 [02 §T2/T3](02-mechanical子技能迁移.md))
- ❌ 不碰 Dave Cowden / Peter Corke 哲学文档(只搬位置)
- ❌ 不用 git LFS(viewer dist 13M 在 git 限内,直接 commit;[03 §10 已决](03-viewer多引擎子技能.md))
- ❌ 不实现 PCB 域代码(P3 留位,[06](06-电子域扩展-pcb-eda-drc.md))
- ❌ 不 npm install(viewer 用 node 直跑 server.mjs,dist 是预构建产物)
- ❌ 不让子技能之间直接互引用 references(原则 3,CI 红线)
- ❌ 不在 super skill 内放产物 `output/`([08 §6 决议](08-shared跨子技能协议.md#6-sharedoutput-路径决议应-10-待讨论-q1) 落项目工作区)
- ❌ 不在父 SKILL.md 内嵌方案 / 详细代码(原则 1)
- ❌ 不让子技能脚本直接 `Path("output/...")` 拼字符串(走 `shared.python.handoff.output_paths`)

## 7. 评审与变更流程

任何架构层面的变更分两类:

| 变更类型 | 流程 | 锁定锚点 |
|---|---|---|
| **架构原则 / 骨架变更**(如新增第 12 个子技能、改两层路由为三层、改不做什么清单) | 先改本文 → 通知 01 项目经理同步排期 → Gate 1/Gate 3 评审 → 推 #待审批 | 本文 §3 / §5 / §6 |
| **跨技能接口变更**(handoff 路径、schema 字段、URL 协议、命名约定) | 先改 [08](08-shared跨子技能协议.md) 的对应章节 → 在 [08 §8 CHANGELOG](08-shared跨子技能协议.md#8-变更登记sharedchangelogmd) 登记 → 通知影响子技能 Owner | 08 |
| **单子技能内实现变更**(scripts 重构、references 拆分、tests 扩充) | 子技能 Owner 自决,跑 `pytest skills/<name>/tests/` 通过即可 | 子技能内 SKILL.md |

**Gate 触发规则**(同 [01 §6](01-分工与排期.md#6-人工介入点gate)):

- **Gate 1**:本文(00) + 01 + 08 全员评审通过 → 开 P0 实施
- **Gate 2**:M2 端到端 demo 跑通 → 决定是否进 P1
- **Gate 3**:P3 电子域启动前(涉及长期工具链锁定)

破坏性变更(改字段名/字段类型/枚举值)无论哪类都必须 @tech_lead 评审,且在 [08 §8 CHANGELOG](08-shared跨子技能协议.md#8-变更登记sharedchangelogmd) 用 ⚠️ 标记。
