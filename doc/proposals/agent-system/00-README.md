## 1. 背景:运行期暴露的 4 个症状

在 robot-dog 项目实际运行中,9-10 个员工 agent 协同时反复出现 4 类问题。它们不是孤立的 bug,而是**同一根能力缺位的 4 种表现**——缺一个跨任务、跨员工、跨时间的"agent 上下文 / 状态 / 验证 / 学习"基础设施层。

| 编号 | 症状 | 用户原话 |
|---|---|---|
| **S1** | 失忆 | "agent 不知道之前做了什么,导致错修改" |
| **S2** | 派活断链 | "派完后不提醒他人干活,或自己不去干活" |
| **S3** | 空心交付 | "都认为验证过了,但只是自己验证 / 测试粗验证" |
| **S4** | 不能迭代 | "做出来一点东西,不能自己迭代" |

---

## 2. 根因诊断:都是同一根脊柱缺位

把 4 个症状映射到 agent 系统的能力维度:

```
┌────────────────────────────────────────────────────────────┐
│  神经突触可塑性  (S4)  → 失败教训不入库,下次同样的错再犯    │
├────────────────────────────────────────────────────────────┤
│  免疫系统      (S3)  → 自评不可信,空心交付                 │
├────────────────────────────────────────────────────────────┤
│  肌肉          (S2)  → 派活动作发出后没有状态追踪           │
├────────────────────────────────────────────────────────────┤
│  脊椎          (S1)  → 跨任务无记忆,所以肌肉/免疫/学习都断  │
└────────────────────────────────────────────────────────────┘
```

**关键观察**:这 4 层有严格的依赖链。**没有 S1 的脊椎,后面三层都无所附**:
- 没记忆 → 派活方记不住"我派出去什么活"(S2 修不了)
- 没记忆 → verifier 不知道"上次同样的检查里漏掉过什么"(S3 难做精)
- 没记忆 → 教训写下来也没处放、没人会主动读(S4 学了等于没学)

所以**实施顺序必须是 S1 → S2 → S3 → S4**,不能并发。

---

## 3. 提案的范围划分(3 篇骨干 + 1 篇横切)

把 4 个症状的解法合并成 **3 篇正交的骨干提案**(避免文档过细割裂),再加 **1 篇横切补强提案**收容五个穿越骨干的能力维度(RAG / 工具治理 / 多 agent 编排 / 模型训练判断 / 系统工程):

| 提案 | 覆盖症状/维度 | 核心目标 | 文档 |
|---|---|---|---|
| **提案 1**:上下文与状态层 | S1 失忆 + S2 派活断链 | 让 agent 出场即知"我是谁、本任务发生过什么、我手头有哪些 in-flight 委派" | [`01-context-and-state.md`](./01-context-and-state.md) |
| **提案 2**:验证与门控层 | S3 空心交付 | 把"完成"从"LLM 自评"升级成"独立 verifier + 机器可执行检查 + 人类 gate" 三道闸 | [`02-verification-and-gates.md`](./02-verification-and-gates.md) |
| **提案 3**:自演化学习层 | S4 不能迭代 | 把每次失败 / 修正,变成下次能被检索到的教训;系统会"老去"——越用越知道公司的坑 | [`03-self-evolving.md`](./03-self-evolving.md) |
| **提案 4**:横切系统补强 | RAG / MCP / 多 agent / 模型训练 / 系统工程 | 5 个穿越 1/2/3 的能力维度,补在 prompt token 利用率、工具权限、流转编排、可观测性等横切位置 | [`04-cross-cutting-enhancements.md`](./04-cross-cutting-enhancements.md) |

### 为什么 S1 + S2 合并到提案 1

- 派活的本质是"派活方在这个时间点的 in-flight 状态"——它就是"任务级共享上下文"的一部分
- 两者共享同一个数据底座(任务上下文 + 委派状态都进 `task_context` 和 `delegations` 两张表)
- 拆成两篇会重复说"prompt 自动注入机制",合并后接口更内聚

### 为什么 S3 单独一篇

- 验证机制有独立的判定模型(verifier agent + ground truth checker + human gate),数据流和 S1/S2 不同
- 跨多个员工角色(每种交付物都要写 ground truth check),实施细节多

### 为什么 S4 单独一篇

- 学习是 S1-S3 都跑通后的二阶能力——它消费 S1 的记忆库 + S3 的验证结果
- 自带一套独立的 cron / 评测体系
- 单写一篇便于把"评测体系"作为独立投资讨论

### 为什么需要"提案 4 横切补强"

- 1/2/3 是脊柱-免疫-学习的骨干,但 5 个横切维度(RAG / MCP / 多 agent / 模型训练 / 系统工程)不属于任何一根脊柱
- 每个横切维度都同时碰多个骨干提案,塞回 1/2/3 会破坏其叙事
- **明确判断**:5 个维度只有 MCP 治理 + 基础可观测性是 P0,RAG / 多 agent 是 P1,模型训练 30 天内不做(P2)

## 4. 提案之间的依赖关系

```
┌───────────────┐       ┌───────────────┐       ┌───────────────┐
│   提案 1      │       │   提案 2      │       │   提案 3      │
│ 上下文+状态层  │ ────▶ │ 验证+门控层    │ ────▶ │ 自演化学习层   │
│ (S1+S2)       │       │ (S3)          │       │ (S4)          │
└───────┬───────┘       └───────┬───────┘       └───────┬───────┘
        │                       │                       │
        ▼                       ▼                       ▼
   task_context          verifier_runs             lessons
   delegations           acceptance_checks         pattern_extracts
   employee_memory       gate_approvals            evals_runs
                                                    │
                        ┌──────────────────────────┘
                        ▼
                  retro_agent 消费上面所有表

       ┌───────────────────────────────────────────────────┐
       │ 提案 4 · 横切系统补强(RAG/MCP/多agent/训练/工程)   │
       │   §1 RAG  →  喂提案 1 prompt header              │
       │   §2 MCP  →  接提案 2 沙箱 + 提案 3 失败队列      │
       │   §3 多 agent  →  推进提案 1 派活 + 提案 2 gate   │
       │   §4 模型训练  →  消费提案 3 evals 数据(P2)      │
       │   §5 系统工程  →  监控 1/2/3 SLO                 │
       └───────────────────────────────────────────────────┘
```

**硬依赖**(下一个提案的前提):
- 提案 2 假设提案 1 的 `delegations.status='done'` 事件可靠触发——所以**先做提案 1**
- 提案 3 的 `retro_agent` 输入需要提案 2 的 `verifier_runs` + `acceptance_checks`——所以**先做提案 2**
- 评测系统(在提案 3)需要提案 2 的"acceptance check 通过率"做主指标——所以**先做提案 2**

**软依赖**(可并行但有协同):
- 提案 1 的"任务级共享上下文"和提案 3 的"教训自动注入"都改 prompt 拼接逻辑——可以做提案 1 时就预留 hook,等提案 3 落地时直接接

## 7. 评估口径(怎么知道做完了有效)

整套提案的**北极星指标**:

| 指标 | 当前 baseline(估) | 目标(整套提案落地后)|
|---|---|---|
| 任务"声称完成"到"真实可用"差距率 | ~40-60%(空心交付率)| < 10% |
| 同一类错误重复发生次数(月)| 高(无统计)| 持平或下降 |
| 派活后超 SLA 未推进的比例 | ~30-50% | < 5% |
| 任务平均迭代轮数(收敛轮数)| 高且发散 | 下降 30%+ |
| Token 消耗(同等复杂度任务)| baseline | 下降 20-40%(prompt 注入更精准 → 少绕路)|
| Agent 自评准确率(对比验收结果)| ~50-60% | 不再依赖,改用 verifier + ground truth |

具体每个提案的 SLI / SLO 见各自文档第 8 节。

## 8. 阅读顺序建议

如果你只有 30 分钟:
1. 先读本 README 的 §2 + §3(理解为什么是 3 篇)
2. 跳到提案 1 的 §1 + §2(看 S1+S2 的方案要点)
3. 浏览提案 2 的 §3(看验证三闸的数据模型)
4. 提案 3 §4(看 retro 的输入输出契约)

如果要决策"先做哪个 / 投入多少":看本 README §5 时间表 + §7 指标。

如果要 review 实现细节:按 1 → 2 → 3 → 4 顺序通读;提案 4 五个维度可按 §0 的"实施总原则"独立挑读。
